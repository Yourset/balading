# 巴拉丁多 Agent 防覆盖开发流程

## 1. 目的

巴拉丁主要通过手机向 DSH 下达开发任务，但实际代码仍在主电脑 Windows 仓库中修改。多个聊天会话如果共享同一目录，即使切换了不同分支，未提交文件仍会互相覆盖。本流程把任务、目录、分支、文件归属、提交、合并和发布分开管理。

本阶段只制定规则，不整理当前遗留改动，也不自动创建分支、worktree、提交或发布。

## 2. 当前现场

只读检查时确认：

- 当前主电脑仓库常用位置：`<你的工作区>/balading`。
- 当前只有一个 Git worktree。
- 当前开发分支为 `publish/mobile-20260827`。
- 该分支存在尚未推送的本地提交。
- 工作区同时存在已跟踪修改和未跟踪文件。
- `master` 推送会触发 `.github/workflows/build-apk.yml` 构建 APK。
- 项目包含 Web、VPS Server、Android、Service Worker、版本文件和公开快照发布，多项改动会共享少数核心文件。

因此，在当前现场完成专项归属整理前，不允许把新并行写入任务继续塞进这个目录。

## 3. 为什么仅切分支不够

Git 分支只隔离已提交历史，不隔离同一个目录中的未提交文件。

错误示例：

1. 会话 A 在同一目录修改 `ChatPage.jsx`，尚未提交。
2. 会话 B 在同一目录切到另一分支。
3. A 的未提交改动仍留在目录里，B 继续写入或提交。
4. 最终可能出现覆盖、混合提交、误回退或功能丢失。

正确做法是：**任务分支 + 独立 worktree + 单一负责人 + 共享任务锁**同时成立。

## 4. 电脑目录规划

脚本必须动态获取仓库根，以下仅是当前主电脑示例：

```text
<你的工作区>\
├─ dsh-mobile\                         历史现场/整合目录
└─ dsh-mobile-worktrees\
   ├─ 00123-image-compress\            任务 00123 独立目录
   └─ 00124-speech-cost-monitor\        任务 00124 独立目录
```

约束：

- 一个目录只能绑定一个任务分支。
- 一个可写会话只能进入自己的任务目录。
- DSH 新会话创建时必须把 cwd 指向对应 worktree，不能继续默认指向历史现场。
- worktree 目录不是备份目录；任务完成后是否移除必须经过明确清理批准。
- 不在仓库内部嵌套 worktree，避免构建、搜索和复制工具误扫。

## 5. 分支职责

### `master`

- 线上稳定版本和 APK 构建入口。
- 不直接开发，不接收半成品。
- 推送前必须明确说明会触发正式构建。

### `integration/mobile`

- 已经提交、已完成任务级验证的候选整合版本。
- 只允许整合负责人操作。
- 必须使用独立且干净的整合 worktree。

### `task/<任务号>-<短名称>`

- 一个分支只处理一个可验收目标。
- 一个任务只能有一个写入负责人。
- 同一功能返工优先继续原任务分支和原会话。

### 当前历史分支

`publish/mobile-20260827` 暂时保持原状。它已经含有本地提交和当前工作区改动，迁移前必须另开专项盘点，不能由本规范任务顺手处理。


缺任一关键字段，不进入写入阶段。

## 7. 任务锁设计

### 锁的作用

锁不是为了阻止 Git 合并，而是为了在写入发生前阻止两个 Agent 同时认领相同功能或文件。

### 推荐存储位置

锁状态应放在所有 worktree 都能看到、但不会进入 Git 的本机共享位置，例如：

```text
%USERPROFILE%\.dsh\project-coordination\dsh-mobile\
├─ claims.json
└─ history.jsonl
```

不要把活动锁放在某个任务分支里，否则其他 worktree 看不到最新状态。

### 每条锁至少记录

- 仓库唯一标识。
- 任务号。
- 会话 id。
- 分支和 worktree。
- 功能范围。
- 文件 glob 范围。
- 领取时间、最后心跳、租约到期时间。
- 当前状态和提交号。

### 冲突判断

以下任一情况视为冲突：

- 文件 glob 有交集。
- 同时修改同一个页面或公共组件。
- 同时修改 `web/public/sw.js`、版本文件、锁文件、工作流或发布脚本。
- 两个功能最终都需要改同一套导航、会话状态、Composer、网关入口或存储结构。
- 一条任务的结果是另一条任务的输入。

冲突任务**不强制串行**：各任务在自己的分支上并行开发，**合并时再处理冲突**；若两个功能互相依赖（一条任务的结果是另一条的输入），则按顺序做。不能因为 Git 暂时没有产生文本冲突就判定可以并行，但也不能因为有重叠就要求排队。

### 锁过期

- 会话异常中断后，锁不能立刻被别人强占。
- 先检查会话状态、worktree、`git status` 和最近提交。
- 只有确认无人继续写入，并留下接力记录后才能转交。
- 强制释放锁必须由维护者批准并写入审计记录。

## 8. 写入前版本校验

每次 Agent 读取准备修改的文件时，记录：

- 文件路径。
- 当前 Git blob 或 SHA-256。
- 文件大小和读取时间。
- 当前 HEAD。

真正写入前再次检查。若内容或 HEAD 已变化：

1. 拒绝直接写入。
2. 重新读取文件。
3. 判断变化是否来自当前会话。
4. 不是当前会话的变化就报告冲突。
5. 未经重新规划不得继续。

整文件 `write` 风险最高，应优先使用能匹配旧内容的局部 `edit`。无法匹配说明文件可能已经变化，不能改用整文件覆盖绕过。

## 9. 标准工作流程

### A. 手机提出任务

手机总管先判断：

- 是原功能继续优化，还是独立新任务。
- 是否已有可继续的原会话。
- 是否与活跃任务范围重叠。
- 是否适合并行。

同一功能、bug、页面或文件链默认继续原会话。

### B. 只读预检

Agent 读取 `AGENTS.md`、本流程、架构文档、目标代码和测试，随后报告目标、范围、分支、目录和验收方式。

### C. 领取任务

自动工具检查锁冲突，创建或绑定任务分支与 worktree，并把 DSH 会话 cwd 指向该 worktree。

### D. 开发

- 只修改登记范围。
- 小步读取、小步修改、小步验证。
- 新需求若扩大范围，暂停并重新登记。
- 发现他人改动立即停止。

### E. 任务提交

得到提交授权后：

1. 查看 `git status` 和完整 diff。
2. 显式暂存任务文件或 hunk。
3. 检查 staged diff。
4. 运行对应测试与构建。
5. 新增一个可回退提交。
6. 记录提交号和未完成项。

### F. 整合

得到合并授权后，由整合负责人在干净整合 worktree 中：

1. 核对任务卡、提交号和验证记录。
2. 确认没有活跃文件锁冲突。
3. 按依赖顺序逐个 merge。
4. 出现冲突时停止，只读分析双方意图。
5. 冲突解决方案交由维护者确认。
6. 合并后运行 Web、Server 和必要真实操作验证。

### G. 发布

发布分为四类，必须分别授权：

1. Web 热更新。
2. VPS Server 更新与重启。
3. `master` 推送及 APK 构建。
4. 公共仓库快照发布。

每类发布都记录来源提交、版本号、目标环境、自动检查、线上读回和手机待测项。

## 10. 共享高风险文件

以下文件或区域默认不能由普通并行任务同时修改：

- `web/src/pages/ChatPage.jsx`
- `web/src/pages/ChatsPage.jsx`
- `web/src/components/Composer.jsx`
- `web/src/main.jsx`
- `web/public/sw.js`
- `web/src/version.js`
- `web/public/version.json`
- `server/index.mjs`
- `package.json`、各级 `package-lock.json`
- `.github/workflows/`
- `scripts/`
- Android manifest、Gradle 和签名相关配置

需要触碰这些文件时，任务卡必须显式声明；与其他任务重叠时并行开发、合并时处理冲突。

## 11. 自动化落地阶段

### 阶段 1：规范生效

- 所有 Agent 先读规则。
- 当前项目保持单写入任务。
- 不自动整理历史现场。

### 阶段 2：任务与 worktree 工具

计划增加：

- `task:start`：检查基线、领取锁、创建 worktree 和任务分支。
- `task:status`：手机查看活跃任务、目录、分支和冲突。
- `task:handoff`：记录中断、提交和接力信息。
- `task:release`：完成验证后安全释放锁。

### 阶段 3：写入和提交门禁

- 写入前文件版本校验。
- 禁止在 `master` / 整合分支直接开发。
- 检查暂存范围、任务号和测试记录。
- 检测多任务文件范围交集。

### 阶段 4：手机可视化

巴拉丁任务卡显示：

- 谁正在处理。
- 使用哪个会话、分支和目录。
- 正在修改哪些功能和文件。
- 是否冲突、阻塞或等待选择。
- 最近提交与验证结果。
- 是否可以继续原任务。

## 12. 当前遗留现场的后续专项

本规范落地后，另开一个只处理历史现场的任务：

1. 冻结当前工作区，不再增加新改动。
2. 按提交和 diff 识别已有成果。
3. 把已跟踪修改和未跟踪文件按功能归组。
4. 标记每组来源会话、验证状态和是否仍需要。
5. 由维护者决定提交、拆分、迁移、保留或放弃。
6. 没有明确决定前，不删除、不回退、不自动合并。

## 13. 验收标准

规范和工具最终达到以下结果才算有效：

- 任意时刻能从手机看到所有活跃写入任务。
- 一个会话无法写入其他任务目录或已锁文件。
- 同一目录不会被两个写入会话同时使用。
- 旧版本文件不能直接覆盖新版本。
- 提交能追溯到任务、会话、文件范围和测试证据。
- 合并冲突不会被自动选择一方覆盖。
- 发布能够追溯到明确提交和版本。
- Agent 中断后可以安全接力，不依赖聊天记忆猜进度。
